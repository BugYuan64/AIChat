# 同类项目功能借鉴分析

- 整理日期：2026-10-26。
- 对照对象：Cumora、Grix、OpenAgents 与 AIChat 当前实现。
- 文档性质：功能调研与候选建议，**不是已批准需求、实施契约或完成验收记录**。

## 二、先对齐 AIChat 已有能力

AIChat 当前已进入实施阶段，技术栈为 uni-app + Vue 3 + TypeScript、Python + FastAPI、PostgreSQL，以及独立 Python 连接器；不是最初仅有设计稿的状态，也不再以 NestJS 作为当前服务端实现。[1]

以下能力不应重复列为全新建设目标：独立的人类/AI 身份、私聊和群聊、结构化 `@`、任务状态卡、停止/重试、扫码配对，以及模型 API 和外部连接器两条接入通路。可结合现有 [AI 详情页](../apps/mobile/src/pages/agents/detail.vue)、[聊天页](../apps/mobile/src/pages/chat/chat.vue)、[任务详情页](../apps/mobile/src/pages/runs/detail.vue) 和 [实施契约](../contracts/PROTOCOL.md) 审查具体改进点。

当前 README 仍明确标注群邀请接收 UI、真实模型厂商/执行型 Agent 接入及 Android 真机验收待完成；这些现有闭环优先于新增复杂功能。接入框架存在，不等于 Hermes、Codex、Claude、Gemini 或 ZCode 已成功接通。[1]

## 四、近期最值得参考的功能

### 1. Agent 健康、设备与能力卡

**场景**：用户只看到“在线”，却不知道 Agent 跑在哪台电脑、模型是否可调用、为什么迟迟不回复。

**参考证据**：OpenAgents 的健康解析区分安装、登录和就绪等状态；Grix 的 Agent 协议包含能力协商；Cumora 的 BYOA 将 Agent 与执行宿主关联管理。它们分别提供诊断分层、能力声明和宿主分离的参考，并不共同构成已经验证过的 AIChat 接入方案。[9][5][2]

**AIChat 最小借鉴**：增强现有 AI 详情页，分别展示执行通道、执行设备、在线/忙碌/排队状态、最近调用结果和脱敏错误，以及流式、取消、工具调用、审批等能力。将设备连通与模型调用成功分开。示例“设备在线，但模型资源不足”只是界面状态示意，不是本次测试结果。

**边界**：能力声明仍需实际适配和验证；Ready 不代表任务已成功运行。更换宿主可以保留 AI 联系人身份，但一期仍保持一个有效绑定，不急于多设备并发。连接器离线不能静默切换到另一个收费模型通道。

### 2. 升级现有任务卡，展示执行阶段

**场景**：用户能看到“运行中”，但不知道是在检查文件、调用工具、测试，还是等待人工确认。

**参考证据**：Grix 有工具过程卡预留、去重和交互卡判别等处理，可参考它将过程事件与普通聊天正文分开的方式。[6]

**AIChat 最小借鉴**：在已有任务卡上展示“检查文件 → 运行测试 → 等待确认 → 已交付”等阶段；每一步可折叠查看脱敏摘要、失败原因和下一步动作。保留现有停止/重试，不另建平行任务系统；接入真实执行型 Agent 后再逐步展示事件。

**边界**：状态必须来自可信执行事件，不能由 UI 猜测。完整工具日志、秘密参数、模型思维链不应直接广播到群聊。停止请求不等于工具已停下，更不等于外部副作用已回滚；结果未知时应如实显示。

### 3. 聊天中的待处理卡

**场景**：Agent 已经暂停等用户回答或批准，用户却必须翻聊天记录才能找到等待点。

**参考证据**：Grix 的交互卡和审批命令桥接将人工处理关联到执行过程；OpenAgents 也有审批及后续恢复处理。代码存在不代表应照搬其全部权限或默认设置。[6][7][12]

**AIChat 最小借鉴**：区分“需要补充信息”和“需要批准操作”，从聊天或任务详情直接回答、批准、拒绝。只读聊天阶段可先做补充信息卡；开放写文件、命令、提交或推送等能力前，再完成真正的操作审批。

**边界**：审批绑定具体任务和不可变操作，核验批准人权限、有效期、一次性消费，并由执行器在执行前再次核对。普通聊天里的“同意”不是授权；群成员身份也不自动授予某台设备的操作权限。界面有批准按钮，不等于已具备安全边界。

## 五、下一阶段值得加入的功能

### 4. 消息转任务与人工确认交接

**场景**：把聊天中的一句需求交给 AI 执行，完成后再交给另一个 AI 审查，但人类仍掌握开始和继续的决定权。

**参考证据**：OpenAgents 将任务记录、分配执行者和启动执行分开；指定负责人不等于立即开始执行。[10]

**AIChat 最小借鉴**：长按消息“转为任务”，选择执行 AI，再点击“开始”；完成后手动选择“交给另一个 AI 审查”。例如“AI A 实现 → AI B 审查 → 人类决定是否继续”，具体厂商接入仍须另行验证。

**边界**：先做人工确认的两步交接，不先做自动互聊。下一位 AI 只获得当前会话授权的摘要与产物，不继承其他私聊、全局记忆或操作权限。新一次执行有独立的任务身份和审计关联。

### 5. 成果卡与会话产物区

**场景**：报告、文件、代码差异和测试结果散落在长聊天里，无法判断来自哪个任务或哪个 AI。

**参考证据**：OpenAgents 的文件接口包含线程归属及读取权限检查，可以参考成果与工作上下文关联的方式；不能据此假定其全部默认共享设置适合 AIChat。[11]

**AIChat 最小借鉴**：用成果卡展示报告、文件、差异、图片和验证结果，记录生成 AI、来源任务和消息，并提供预览。初期只做会话内产物，不建设完整网盘或复杂知识库。

**边界**：每次下载重新鉴权，退群或撤权后不能继续借旧链接读取。只发布明确选定的产物，不默认开放 Agent 的工作目录；文件存在或填写了验证说明，也不等于测试已经通过。

### 6. 防止继续回答过时的需求

**场景**：AI 按方案 A 执行时，用户已经明确改为方案 B，随后收到的仍是旧要求的结果。

**参考证据**：Cumora 的部分群聊回复路径检查未见新消息，必要时返回暂缓发送的结果，让 Agent 复核；代码中的群聊范围和逐字去重条件不能泛化成全部会话的语义去重保证。[3]

**AIChat 最小借鉴**：用户明确修改需求或停止任务时，标记旧运行可能过时，让用户选择停止、查看旧结果或按新要求另开运行。

**边界**：保留当前固定任务上下文的原则，不静默替换在途任务的上下文。普通群消息不应一律触发重算；写操作结果未知时不能借“按新要求重试”自动重放。

## 六、稍后按需求决定的功能

### 7. 群级 AI 回复策略

**场景**：有些讨论只想在明确 `@` 时唤醒 AI，有些短时协作希望 AI 持续关注一段讨论。

**参考证据**：Cumora 有 mute/follow 等群聊注意力控制，可参考“是否关注讨论”与“是否实际回复”的区分。[3]

**AIChat 最小借鉴**：保留默认“人类明确 `@` 才执行”，后续再提供限时跟随讨论及清晰的关闭入口。

**边界**：跟随有时限、预算和发言上限；不能把引用消息顺便改为自动触发，也不能与人类消息免打扰混为一谈。AI 提及另一 AI 不自动授予递归执行权。

### 8. Android 通知与统一待办入口

**场景**：App 退到后台后，用户希望知道任务完成、失败或需要人工处理，点击后直接回到对应任务。

**参考证据**：Cumora 有统一的消息通知路径，Agent 回复也可以进入通知处理。[4]

**AIChat 最小借鉴**：统一展示“任务完成、任务失败、等待回答/批准”，点击直达任务或消息，并提供待办列表，避免未处理事项淹没在聊天中。

**边界**：WSS 在线不等于用户正在看当前会话，也不等于 Android 后台通知可靠。需单独真机验证前后台、杀进程、弱网和点击恢复；锁屏默认不展示敏感正文。尚未实现推送时，只能承诺已验证的前台恢复能力。

## 七、暂不照搬的设计

1. **每个 Agent 一套重型云执行环境**：当前不引入 Kubernetes Pod、FUSE 等复杂部署，不因借鉴宿主概念就照搬整个执行基础设施；Cumora 的宿主和部署方案仅作为研究参考。[2]
2. **自主无限互聊和复杂多模型分诊**：先保证人类明确触发、可追踪、可停止；是否引入自动协作应另行确认，不在此次报告中扩大首期范围。
3. **默认共享全部上下文、记忆和文件**：借鉴工作区产物组织，不借此改变 AIChat 的私聊、群聊、历史和设备权限边界；尤其不照搬不适合当前产品的文件共享默认值。[11]
4. **把审批卡当成授权实现**：卡片只是入口，执行器的权限检查才是边界。
5. **直接复制 Grix 代码和素材用于自己的 App**：其 LICENSE 是自定义许可，不能按默认 MIT 理解；实际代码复用、商业使用或分发前须审阅适用条款。本报告推荐功能思路，不构成代码复用授权。[8]

## 八、建议推进顺序与本次交付边界

建议顺序：

**补齐现有聊天闭环和真实接入 → 健康诊断、任务/待办体验 → 成果卡与人工交接 → Android 通知 → 最后评估有限自动协作。**

其中，“现有聊天闭环”包括当前仍待完成的群邀请接收等产品路径；真实接入和 Android 验收不能用模拟 adapter 或文档勾选替代。[1]

落地时沿用现有技术栈和 [实施契约](../contracts/PROTOCOL.md)。若选择实施某项候选功能，再单独确认范围、修改契约、增加实现和执行对应验证；本报告不修改产品需求、不更新阶段完成状态，也不声明任何新增功能已经可用。

本次落档仅包含本报告与 README 文档入口，不包含业务代码、依赖安装、部署变更或第三方代码复制。

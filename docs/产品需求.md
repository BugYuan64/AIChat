# AIChat 产品需求

日期：2026-10-28（v2，方向收窄）。状态：已按用户明确目标重定范围，取代 2026-10-24 v1 设计稿。

## 1. 产品定位

**AIChat 是一个远程控制面：人在手机上，对运行在固定 Linux 主机上的 CLI Agent 下达指令并持续对话。**

一句话定义：把 VPS 上的 `zcode` / `codex` / `hermes` 这类终端 Agent，装进联系人列表，随时用手机与它对话、派活、看进度。

### 1.1 核心模型：一个实例 = 一个 AI 账号 = 一个会话

这是本产品的唯一架构支柱，其余设计都由它推导：

| 概念 | 落地形态 |
| --- | --- |
| 一个实例 | 主机上一份可续接的 agent 会话（一个 `sessionId`） |
| 一个 AI 账号 | AIChat 里的一个 `kind=ai` 账号，有 handle、昵称、头像 |
| 一个会话 | 该账号与人类之间唯一的那条私聊 |

绑定关系是 1:1:1，且由服务端强制：

- `Connector` 表只有单个 `agent_account_id`，一个连接器进程只服务一个 AI 账号；
- `RuntimeBinding` 主键即 `agent_account_id`，一个 AI 只有一条绑定；
- 对同一 AI 重复配对会撤销旧连接器、中断在途任务，**第二个实例会踢掉第一个**。

因此"想再开一个 agent"在操作上等于"再建一个 AI 账号"。这不是绕路，这是产品语义：它们在联系人列表里本来就该是三个不同的 AI。

### 1.2 与 MCP 的区别

本产品**不是** MCP，也不是把 MCP 包一层。

| | MCP | AIChat |
| --- | --- | --- |
| 谁主动 | AI 是主语，主动发现并调用工具 | AI 是宾语，平台把人说的话推给 AI 执行 |
| 交换单位 | 一次 tool call（结构化参数进、结构化结果出） | 一轮对话（会话上下文进、自然语言流式文本出） |
| 身份模型 | 无身份概念 | AI 有账号、owner、授权、成员身份 |
| 产出归宿 | 返回给模型作为推理素材 | 落库成聊天消息给人看 |

准确的内部定位：**反向托管的 chat completions 端点**。`model_api` 模式下"供应商"是智谱/OpenAI，`connector` 模式下"供应商"就是主机上的那个 CLI。两条路往同一个 `response_message_id` 写增量。

## 2. 目标与非目标

### 2.1 目标（必须达成）

| 目标 | 验收含义 |
| --- | --- |
| 连接主机上托管的 agent | 连接器进程常驻，能拉起并接管 CLI 会话，跨任务保持同一上下文 |
| 双向对话 | 人发消息 → agent 执行 → 流式回传 |
| 远程下达指令 | 手机发出的自然语言指令能真正驱动 agent 执行有副作用的操作 |
| 会话持久 | 连接器重启、网络中断后，会话仍可续接，历史不丢 |
| 过程可见 | 能看到 agent 在改哪个文件、跑哪条命令、卡在哪里 |

### 2.2 非目标（明确不做，不再讨论）

以下条目从 v1 设计稿中移除，因为它们偏离"远程控制面"这一目标：

| 移除项 | 原因 |
| --- | --- |
| 人类—人类私聊、联系人互加、拉黑 | 本产品不服务人际沟通 |
| 多人群聊、群角色、群邀请、群主转让/解散 | 群聊是 v1 的中心，现在不是 |
| AI—AI 协作、多 AI 群内讨论、轮次与预算 | 复杂度过高，且当前无使用场景 |
| @ 触发规则、单条最多 @3 个 AI | 无群聊即无此规则 |
| 模型 API 直连（`model_api` 模式） | 与"连接运行中的 agent"目标无关；保留代码但不作为产品路径，不再扩展 |
| 公开注册、第三方登录 | 单人使用场景 |
| 朋友圈、支付、语音视频、图片文件多模态 | 与目标无关 |
| Android 打包与小程序适配 | 先以 H5 跑通，客户端形态后议 |
| 端到端加密承诺 | 服务端需要处理消息，不承诺 |
| 计费、额度、token 结算 | 单人自用，无商业需求 |

同时移除 v1 中"首版默认禁用命令执行与文件写入"这一条——它与本产品的存在目的直接冲突。改为：**能力默认开启，靠权限模式与授权控制**（见 §6）。

## 3. 部署形态

```
[手机 H5]
    │ HTTPS / WSS
    ▼
[AIChat 服务器]  ← 公网可达，已有部署
    ▲
    │ 出站 WSS 长连接（连接器主动拨出，服务端从不主动连入）
    │
[connector-runner]  ← 常驻在目标 Linux 主机（systemd / tmux）
    │
    ├── 本地进程 spawn / resume
    ▼
[zcode / codex / hermes 实例]  ← 由连接器托管
```

两条连接必须分清，不能混为一谈：

- **出站长连接**（连接器 ↔ 服务器）：跨公网，反向拨出，NAT 友好，不用开端口。已实现且完整（配对、凭据轮换、心跳、退避重连、fencing）。
- **本地会话**（连接器 ↔ agent）：不走网络，走子进程 spawn。**这是当前缺失的一半。**

### 3.1 目标主机

- Ubuntu 24.04 LTS，2 核 3.7G 内存，`35.73.46.1`，用户 `hermes`。
- **不得触碰已在运行的 hermes gateway 实例**（PID 1635186，仅监听 `127.0.0.1:55257`）。新实例一律独立配置目录、独立凭据、独立账本。

## 4. 已验证的 CLI 能力

2026-10-28 在目标 VPS 实测，以下为**已验证事实**，不是文档推测：

| CLI | 版本 | 路径 | 已验证能力 |
| --- | --- | --- | --- |
| zcode | 0.17.0 (CLI 3.16.2) | `/home/hermes/.local/bin/zcode` | `-p` 一次性、`--json` 返回 `sessionId`、`--resume <sess_...>` 跨目录续接、`-c` 续最近会话、`--mode` 权限分级、写入文件、执行 shell |
| codex | 0.165.0 | `~/.codex/packages/app-server-daemon/releases/*/bin/codex` | `app-server`（JSON-RPC、默认 stdio）、`exec` 非交互、`resume`、`agents` |
| hermes | v0.22.5 | `~/.hermes/hermes-agent/hermes` | `serve`（JSON-RPC/WebSocket gateway，默认 `127.0.0.1:9119`）、一次性模式 |
| claude | 未安装 | — | — |

### 4.1 zcode 实测记录

```
# 会话创建，返回 sessionId
$ zcode -p 'Remember the number 4242.' --mode plan --json
{"sessionId": "sess_3fc69bb8-...", "response": "OK. Noted — 4242.", ...}

# 跨目录续接，上下文保持
$ cd /tmp && zcode -p 'What number did I ask you to remember?' --json --resume sess_3fc69bb8-...
{"sessionId": "sess_3fc69bb8-...", "response": "4242"}

# 写入副作用（edit 模式）
$ zcode -p 'Create proof.txt containing: hello-from-zcode' --mode edit
→ 文件确实被创建，内容正确

# shell 执行（yolo 模式）
$ zcode -p 'Run: echo YOLO_TEST_OK' --mode yolo
→ "The command ran successfully"
```

**关键结论：**

1. **`-p` 每次都是独立进程，实测约 10 秒冷启动。** 这是选型的硬约束：不能用"一个长驻进程接多轮"的模型，必须用"每次 spawn + `--resume` 续接"的模型。
2. **会话状态在磁盘上，不在进程内存里。** 所以连接器重启后仍能续接，只要存住 `sessionId`。
3. **`--mode` 决定审批行为，`-p` 默认就是 `yolo`（全自动批准）。** 这消除了 v1 担心的"审批卡死"问题，但也意味着**权限控制必须由平台侧显式选择 mode 承担**，不能让默认值滑过去。
4. 输出有非 JSON 噪声行（`ZCode Built-in skipped (not-due)`），适配器必须逐行解析 JSON 对象而不是整体 `json.loads`。

### 4.2 尚未验证

- codex app-server 的实际 wire 格式（文档说双向 JSON-RPC、默认 stdio JSONL，本机未跑通握手）
- hermes `serve` 的认证方式与 API schema
- 长任务（>2 分钟）的实际行为、中途取消的响应时间、并发同一 session 的行为

## 5. 会话模型

### 5.1 会话标识与续接

连接器为每个 AI 账号维护一条**本地会话记录**，落盘在账本里：

| 字段 | 用途 |
| --- | --- |
| `agent_account_id` | 哪个 AI（实际上一进程只有一个，保留以支持将来多账号） |
| `adapter_kind` | zcode / codex / hermes，决定续接命令怎么拼 |
| `external_session_id` | CLI 侧的会话标识（如 `sess_...`） |
| `cwd` | 该会话的工作目录，续接时必须一致 |
| `last_run_at` | 用于清理陈旧会话 |

续接规则：

- 会话存在 → `zcode -p '<新指令>' --resume <id> --cwd <cwd>`
- 会话不存在或续接失败 → 新建会话，记录新 id，并在聊天中提示"已开启新会话"
- **绝不把 AIChat 的 `context` 全量重放进 CLI**：历史已经活在 CLI 自己的会话里，重放会导致重复上下文。只发送**最新一条用户消息**。

### 5.2 与 AIChat 会话的关系

本版本采用最简映射：**一个 AI 账号只有一条私聊，这条私聊对应唯一的 CLI 会话。** 不需要 `conversation_id → session` 的多路映射，因为不有多群。

`build_offer` 里已有的 `conversation_id` 仍应传到适配器——为将来多会话留扩展位，且顺带修掉 `system_prompt` 丢失的既有缺陷。

### 5.3 并发约束

同一 AI 同时只执行一个 run（服务端 `runs/service.py` 的 `agent_account_id.not_in(active)` 已强制）。这条约束对本产品**是正确的，不是限制**：一个 CLI 会话本就不能并发处理两条输入。保留不动。

`core/config.py` 的 `max_agent_concurrent_runs` 是死配置（定义后从未被引用），应删除，不留误导。

## 6. 权限与审批

CLI agent 有真实的文件写入与命令执行能力。权限控制落在三处：

### 6.1 CLI 权限模式

连接器为每个 AI 账号配置一个权限模式，映射到 `--mode`：

| 平台配置 | zcode | 含义 |
| --- | --- | --- |
| 只读/建议 | `plan` | 只能读和规划，不能改 |
| 可控写入 | `edit` | 能改文件，命令执行仍需谨慎 |
| 完全委托 | `yolo` | 自动批准一切 |

**平台默认必须是 `plan`，不得继承 `-p` 的 `yolo` 默认值。** 由所有者在 AI 详情页显式提升。默认值写在代码里，不写在文档里。

### 6.2 授权

只有 AI 所有者和被显式授权的人类账号能触发该 AI。复用现有的 `AgentGrant` 机制，默认只有所有者本人。

### 6.3 副作用告知

聊天中每次 run 开始前显示：`以 <模式> 权限在 <cwd> 运行`。执行完成后显示变更摘要（改了哪些文件、跑了哪些命令），而不是把所有过程文本刷进气泡。

### 6.4 决定不做的事

- **不做逐动作审批弹窗。** `-p` 是一次性进程，中途拦截需要 PTY + 双向 stdio 注入，工程成本极高且脆弱。改用"运行前选模式"来前置控制。
- **不实现 tool approval 协议帧。** v1 协议定义的 `tool.approval.request/result` 在本版本不实现，协议文档中标注为"未实现/预留"。

## 7. 长任务与超时

现有默认值对本产品完全不可用：`run_deadline_seconds = 120`，正常改一次代码就会超。

| 参数 | 现值 | 目标值 | 理由 |
| --- | --- | --- | --- |
| `run_deadline_seconds` | 120 | 1800 | 真 agent 干一次活常需数分钟 |
| `run_queue_deadline_seconds` | 300 | 3600 | 排队等待不能比执行还短 |
| `max_output_bytes` | 256 KiB | 保留 | 足够 |
| `max_context_messages` | 30 | 不再使用 | 不再从 DB 重建上下文 |

同时必须修掉两个既有缺陷：

1. **字段名错配**：连接器读 `policy["deadline_at"]`，服务端写的是 `policy["deadline_seconds"]`，导致连接器侧超时检查恒为 `None`、从未生效。两边认知不一致是最难排查的 bug。
2. **超时后尸体清理**：服务端 135 秒后把 run 判为 `recovery_required`，但连接器那边的 CLI 进程还在跑。必须实现"服务端超时 → 下发 cancel → 连接器杀进程组"的闭环。

## 8. 过程可见性

v1 把一切产出压进一条聊天消息。对 CLI agent 这不可用（30 分钟任务实时刷气泡）。

改为两级呈现：

| 层级 | 内容 |
| --- | --- |
| 聊天消息 | 开始提示、进度摘要（可折叠）、最终结果（Markdown） |
| 运行详情页 | 完整过程：命令、文件变更、token 用量、耗时、session id |

CLI 的 `--json` 输出里已有 `usage`（输入/输出/缓存 token）、`projection`（轮次、上下文占用）、`traceId`，直接映射到运行详情。

增量推送策略：`-p` 模式拿到的是完整响应而非 token 流，因此不逐 token 推；改为**心跳式进度**——连接器每 15 秒推一次"仍在运行 + 已用时长"，避免用户以为卡死。

## 9. 页面职责

| 入口 | 核心内容 |
| --- | --- |

| 聊天页 | 消息流、指令输入、停止按钮、运行中横幅 |

| AI 详情 | 权限模式、工作目录、会话标识、重新配对、撤销绑定 |

| 运行详情 | 完整过程、token、耗时、失败原因 |

移除：联系人与群相关全部页面（群设置、群邀请、成员管理、@ 选择器）。

## 10. 实施优先级

按依赖顺序，每步都可独立验收：

| 顺序 | 工作 | 位置 | 阻塞后续 |
| --- | --- | --- | --- |
| P0 | 抬高时限 + 修字段错配 + 超时杀进程 | `core/config.py`、`runs/service.py`、`connector/ws.py` | 是 |
| P1 | 账本加 `sessions` 表 | `connector/ledger.py` | 是 |
| P2 | `build_offer` 补 `system_prompt` + `conversation_id` | `runs/service.py` | 否 |
| P3 | 写 zcode 适配器（spawn + resume + 逐行解析 JSON） | `connector/adapters/zcode.py` | 否 |
| P4 | 权限模式配置与 UI | `agents/`、`apps/mobile` | 否 |
| P5 | 运行详情页与进度心跳 | `apps/mobile`、`connector/ws.py` | 否 |
| P6 | codex 适配器 | `connector/adapters/codex.py` | 否 |
| P7 | hermes 适配器 | `connector/adapters/hermes.py` | 否 |

P0-P3 完成即达成"能连上、能对话、能派活"的最小闭环。

## 11. 验收标准

| 编号 | 场景 | 通过条件 |
| --- | --- | --- |
| A1 | 配对 | 手机上批准后连接器上线，AI 详情显示在线 |
| A2 | 单轮对话 | 手机发消息，60 秒内收到 agent 回复，内容正确 |
| A3 | 会话续接 | 连发两条消息，第二条 agent 能记住第一条的内容 |
| A4 | 跨重启续接 | 重启 connector-runner 后发消息，仍记住之前的对话 |
| A5 | 指令执行 | 指令"创建 test.txt"能真实落地到主机文件系统 |
| A6 | 权限生效 | `plan` 模式下要求写文件，agent 拒绝或只给方案，文件不产生 |
| A7 | 长任务 | 运行超过 5 分钟的任务不被打断，完成后结果正确 |
| A8 | 取消 | 点停止后 30 秒内 agent 进程确实退出（`ps` 验证），且无残留 |
| A9 | 断线恢复 | 拔网 1 分钟后恢复，消息不丢、不重复执行 |
| A10 | 不干扰 | 全程不影响已在运行的 hermes gateway（PID 1635186 不重启、日志无异常） |

## 12. 风险与已知缺口

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| `-p` 冷启动 10 秒 | 每条消息延迟高 | 接受；未来可评估 app-server 常驻 |
| 无中途注入 | 不能对运行中的 agent 追加指令 | 接受，本版本不做；靠 cancel + 重新下发 |
| 会话损坏不可恢复 | `--resume` 失败会丢上下文 | 检测失败后自动新建并提示 |
| 同一 session 并发 | 未验证行为 | 服务端串行已规避 |
| codex/hermes 接口未验证 | 适配器可能返工 | 先做 zcode，跑通再逐个验证 |
| 权限默认值滑落 | `yolo` 被误用 | 平台侧默认 `plan`，写入代码而非文档 |
